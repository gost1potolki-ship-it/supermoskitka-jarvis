# SuperMoskitka Jarvis — правила разработки

## Обязательные документы

Перед началом любой задачи сначала прочитать:

1. `docs/JARVIS_CORE_V1.md`
2. текущий файл задания `TASK_XX...md`, если он передан пользователем

`docs/JARVIS_CORE_V1.md` определяет общую архитектуру, границы продукта и принятые системные решения.

Текущий TASK определяет только конкретный этап реализации.

Если локальное задание явно противоречит `docs/JARVIS_CORE_V1.md`, не угадывать и не обходить противоречие самостоятельно. Остановиться и сообщить пользователю.

## Scope

Не реализовывать функции следующих этапов самостоятельно.

Не добавлять архитектурную сложность "на будущее", если она не требуется текущим TASK.

Не подключать внешние сервисы, базы данных, LLM, каналы или инфраструктуру, если текущий TASK этого прямо не требует.

## Existing code

Не ломать уже принятые доменные модели и тесты без прямого требования текущего TASK.

Перед изменениями изучить существующую реализацию, чтобы не создавать параллельные типы, дублирующие интерфейсы или второй источник истины.

## Quality gate

После каждого задания обязательно выполнить:

```bash
npm run build
npm run lint
npm test
```

Все команды должны завершиться успешно.

## Git workflow

Одна завершённая задача = один отдельный Git commit.

После успешной проверки:

```bash
git add .
git commit -m "<понятное сообщение текущей задачи>"
git push
```

После push создать review patch:

```bash
git format-patch -1 HEAD --stdout > TASK_XX_REVIEW.patch
```

Review patch не добавлять в Git.

После создания patch проверить:

```bash
git status
```

## Stop rule

После выполнения текущего TASK остановиться.

Не начинать следующий этап без отдельного задания.
